## Branches or worktrees

A project is either a **Repo** or a **Bare** project (see
[Spaces, projects and branches](/docs/workspace/spaces/#projects)):

- In a **Repo**, every branch shares one working folder. Only one branch is
  checked out at a time, and switching branches changes the files under every
  agent and terminal working there.
- In a **Bare** project, every branch is checked out in its own folder, a
  worktree, beside the others. Two agents on two branches never touch each
  other's files, and switching between them checks nothing out.

Use **Bare** for anything where agents work in parallel. Create one with **New
in "space"** > **Clone**, where **Worktree layout** is on by default, turn a
folder into one with **Initialize git** > **Bare + worktree**, or convert an
existing clone with
[**Convert to worktree layout**](/docs/workspace/spaces/#convert-a-clone-to-the-worktree-layout).

## Add a branch or worktree

<Steps>

1. Right-click the project and choose **Add branch** (Repo) or **Add
   worktree** (Bare).
2. In **Add branch in "api"** (or **Add worktree**), type in the filter. The
   list shows every branch on disk, local and remote together, told apart by
   their glyph. Branches already checked out say **checked out**, or **in a
   worktree**.
3. Pick an existing branch, or type a new name. A name that matches nothing
   gets its own row, **Create branch** `name` **from** `main`.
4. For a new branch, click the base after **from** to pick where it starts.
   It defaults to the repository's default branch, and the picker filters as
   you type.
5. Press `Enter`, or click the button.

</Steps>

What happens depends on what you picked:

| You picked | In a Repo | In a Bare project |
| --- | --- | --- |
| A local branch | Adds its row. Select it or use **Checkout** to switch | Creates a worktree for it |
| A remote branch | Adds a local branch tracking it | Creates a worktree tracking it |
| A new name | Creates it from the base and checks it out | Creates it from the base, in a new worktree |

A new worktree's folder is named after the branch's last part, so
`bug/critical` gets the folder `critical`. If that folder exists, the folder
uses the whole branch name instead, `bug-critical`; if both exist, Tori refuses
rather than overwrite anything.

The new branch or worktree is selected, and a new worktree opens a
[chat draft](/docs/agents/starting-a-chat/#chats-that-open-by-themselves) so you
can start right away.

### Fresh branches from the remote

The list is read from disk, so it opens at once. Branches pushed to the remote
since the last background fetch are not in it until you click the **Fetch**
button in the list's header. Tori fetches every repository on its own every 10
minutes, and when you come back to the window; set how often with **Git fetch
every** in Settings > Integrations > Remote, or turn it off. A repository whose remote would ask for a password is
skipped by the background fetch rather than prompting you.

### Delete a branch from the list

Hover a local branch that is not checked out and click its trash icon. The
dialog asks **Delete branch** `name` first, and says whether it **has commits
the remote does not**, so you do not lose unpushed work by accident.

## Start from an issue

When the project's host is connected (see
[Pull requests and issues](/docs/git/pull-requests-and-issues/)), the dialog has
a **Branch** and **Issue** switch.

<Steps>

1. Switch to **Issue**. The list shows the issues assigned to you, or the
   project's [issue sources](/docs/automation/autopilot/#issue-sources) when it
   has some. An issue from another repo is shown with its repo, such as
   `gettori/tickets#31`.
2. Pick one, or type an issue number that is not in the list and choose
   **Open issue #214**.
3. The branch name fills in from the issue. Change it if you like, and pick a
   base for a new branch.
4. Leave **Link the branch to the issue on GitHub** ticked to have GitHub
   create the branch and show it on the issue. It is greyed out when the base is
   not on the remote, or the branch already exists here, and a note under it
   says why.
5. Confirm with **Start from #214**.

</Steps>

The branch or worktree is created, its row wears the issue's number (click it
to open the issue), and a chat draft opens with the issue's title and body as
the prompt and a **from #214** link above the composer. Read it, add anything,
and send.

## Worktree settings

Every Bare project's [settings dialog](/docs/workspace/project-settings/) has a
**Worktrees** section: right-click the project, choose **Project settings** and
pick **Worktrees**. It holds what each worktree gets: a setup command when it
is created, a run command you start and stop by hand, a teardown command before
it is removed, and the files shared into it.

### A setup command for new worktrees

A new worktree has only what git tracks: no `node_modules`, no build output,
no generated files. A setup command fixes that.

A repo's commands are under **Tooling** rather than **Worktrees**. The
repository can also propose these commands itself, see
[Commands from the repository](/docs/git/project-config/).

<Steps>

1. Open **Project settings** for the project and pick **Worktrees**.
2. Type the command in **Setup command**, for example
   `pnpm install --frozen-lockfile --prefer-offline`.
3. Press `Enter` or click away to save it.

</Steps>

From then on:

- It runs in every worktree Tori creates for the project: from **Add
  worktree**, from an issue, from [fan out](#fan-out-several-attempts), from
  `tori worktree new` and from the Autopilot.
- It runs with `sh -c` in the new worktree, with `TORI_PROJECT_ROOT` set to the
  project's folder and `TORI_WORKTREE_PATH` to the new worktree.
- It runs in the background, not in a tab. When it ends, a toast says **Setup
  finished in critical**, or **Setup in critical failed (exit 1)** with **Show
  log** to read its output.
- A setup that runs longer than 30 minutes is stopped and reported as failed.
  Removing the worktree stops a setup still running in it.
- A worktree made from a fork's pull request never runs it, since that code is
  not yours.

**Agents started over the socket wait for it**: turn this on to make
`tori worktree new`, `tori spawn` and the Autopilot wait until the command
exits, up to four minutes, so a scripted session does not start work in a half
installed tree. Sessions you start by hand never wait.

The command is kept in your own settings file, keyed by the project, not in
the repository, so a repository cannot give itself a command to run. An empty
field runs nothing.

### A run command for each worktree

The command you start in every worktree, usually the dev server, can be set
once for the project and started from the worktree's row.

<Steps>

1. Open **Project settings** for the project and pick **Worktrees**.
2. Type the command in **Run command**, for example
   `pnpm dev --port $TORI_PORT`.
3. Press `Enter` or click away to save it.

</Steps>

From then on:

- Each worktree row in the sidebar shows a play button while the pointer is on
  it. Click it to start the command in that worktree, and click the square
  that replaces it to stop it. While it stops, the button is greyed out and
  says **Stopping**. Off the row the button stays hidden, and a running
  server shows by its port.
- The command palette has **Start the run command** and **Stop the run
  command** for the worktree in front. Both are listed only for a project with
  a run command. Start says **Already running** while one runs, and Stop says
  **Stopping** while one stops and **Nothing is running here** when nothing
  does.
- It runs in the background, not in a tab, with `sh -c` in the worktree and
  `TORI_PROJECT_ROOT`, `TORI_WORKTREE_PATH` and the worktree's
  [ports](/docs/git/ports/#a-block-of-ports-per-worktree) set. While it runs,
  **Run command** sits at the top of the
  [Scripts](/docs/editor/files/#scripts) section with the command beside it.
  Click it, or right-click for **Show log**, to read its output, and
  right-click for **Stop**.
- With [dev server links](/docs/git/ports/#links-to-running-servers) on, its
  server's port shows on the row a few seconds after it starts listening.
- With **Open the browser when a server starts** on, which it is by default,
  the first port its server listens on opens in your browser, as soon as it
  answers, even with the Tori window hidden. When the server listens on more
  than one port, the worktree's `$TORI_PORT` wins if it is one of them, and the
  lowest port otherwise. That is one tab per start: a second port opens nothing
  until you click it, and a run stopped before it listens opens nothing.
  Tori watches for two minutes after the start. With the [browser
  extension](/docs/browser/extension/#opening-a-server-from-tori) installed,
  restarting the run brings the tab already on that port to the front instead
  of opening another. Turn the switch off in **Project settings** >
  **Worktrees** to start servers quietly.
- With **Start the run command when a worktree is created** on, a worktree you
  create from the sidebar, from a branch or from an issue, starts its run
  command by itself once its setup command finishes without an error, or at
  once when the project has no setup command. Together with **Open the
  browser when a server starts**, making a worktree ends with its app open in
  the browser. A setup command that fails or runs past its 30 minute limit
  starts nothing, and so does picking a branch that already has a worktree.
  Worktrees made by an agent, by `tori worktree new`, for a pull request
  review or as attempts never start it, so a fan out does not start a server
  per worktree. It is off by default, and the switch is greyed out until the
  project has a run command.
- Stopping sends it a polite signal first and gives it five seconds to clean
  up, then ends it. Starting it again while it stops waits for the old one, so
  two servers never fight over one port.
- If it exits on its own with an error, a toast says **Run in critical failed
  (exit 1)** with **Show log**. Stopping it says nothing.
- Removing the worktree stops it before the teardown command runs, and
  quitting Tori stops every run command. If Tori crashes, the next launch stops
  the run commands it left running.
- [Removing worktrees automatically](#remove-worktrees-automatically) never
  removes a worktree whose run command is running.
- A log past 5 MB is cut back to its last 1 MB, and run logs older than a week
  are deleted when Tori starts.
- A worktree made from a fork's pull request never runs it, since that code is
  not yours. Its row has no play button and the palette does not list the two
  commands there.

Like the setup command, it is kept in your own settings file, not in the
repository. An empty field leaves the play button off the rows.

### A teardown command before removal

Some worktrees leave things behind that git knows nothing about: a test
database, a container, a cache outside the folder. A teardown command cleans
them up.

<Steps>

1. Open **Project settings** for the project and pick **Worktrees**.
2. Type the command in **Teardown command**, for example
   `docker compose down --volumes`.
3. Press `Enter` or click away to save it.

</Steps>

From then on:

- It runs before every removal of a worktree in the project: **Remove
  worktree**, [removing worktrees automatically](#remove-worktrees-automatically),
  promoting an attempt (for the attempts that go) and removing a Topic member's
  worktree.
- It runs with `sh -c` in the worktree, while the folder is still there, with
  `TORI_PROJECT_ROOT`, `TORI_WORKTREE_PATH` and the worktree's
  [ports](/docs/git/ports/#a-block-of-ports-per-worktree) set. A setup or run
  command still running there is stopped first.
- The row shows **Tearing down** while it runs.
- A teardown that runs longer than 2 minutes is stopped. Whether it fails or
  is stopped, the removal still goes ahead, and a toast says **Teardown in
  critical failed (exit 1)** with **Show log**. A teardown that works says
  nothing, because the worktree going away already says it.
- A worktree made from a fork's pull request never runs it, since that code is
  not yours.

Like the setup command, it is kept in your own settings file, not in the
repository. An empty field runs nothing.

### Shared files

The same page lists the files shared into every worktree, such as a `.env`.
See [Shared in worktrees](/docs/git/shared-files/).

## Fan out several attempts

Fan out starts two, three or four independent attempts at the same task, each
in its own worktree on its own branch, so you can run an agent in each and
keep the best result.

<Steps>

1. Right-click a Repo or Bare project and choose **Fan out**. The project needs
   at least one commit.
2. Answer **Fan out: what are these attempts for?** with the goal, for example
   `retry webhooks with backoff`. It is kept with the attempts so you can still
   see later what they were for.
3. Pick **How many attempts?**: 2, 3 or 4.

</Steps>

Tori creates the attempts from the current commit, on branches named after the
goal, `retry-webhooks-with-back-1`, `-2` and so on (the first 24 characters of the goal). They live in a hidden
`.tori-attempts` folder inside the project, and show in the sidebar grouped
under one heading with the goal.

To save time, each attempt gets a copy of the project's `node_modules`,
`vendor`, `target` and `.venv` folders if they exist. On macOS this copy is
almost free. A toast lists any of these that could not be copied, so you can
install them in the attempts yourself. The setup command runs in each attempt
too.

Start a chat in each attempt (**New session** on its row, or select it and
open a chat), give each the same or a different prompt, and compare.

### Keep the winner

Right-click the attempt you want and choose **Promote this attempt**.

<Aside type="danger" title="Promoting deletes the other attempts">

The attempt you promote is kept as it is, on its own branch and unmerged. Every
other attempt in the group is deleted outright: its worktree, branch, sessions
and checkpoints. Agents and terminals running in them are stopped. This cannot
be undone.

</Aside>

Promoting never merges anything. Merge or open a pull request from the winner's
branch as you would from any other.

## Remove a worktree or branch

Right-click the row and choose **Remove worktree** (Bare) or **Remove branch**
(Repo, for a branch that is not checked out).

The dialog shows what you are about to remove before you confirm: the branch,
the folder, whether it is **clean**, has **uncommitted changes** or **unpushed
commits**, and how many tabs and agents are running in it. Two options:

- **Delete local branch (git branch -D)**: on by default. Off keeps the branch
  so you can make a worktree for it again later.
- **Delete remote branch (git push --delete)**: off by default. Also deletes it
  on the remote.

Confirming moves the selection to the next worktree in the project (or the
one before it, or the main checkout), stops the tabs and agents running there,
runs the project's [teardown command](#a-teardown-command-before-removal) if
it has one, then removes the worktree and the branches you chose. The folder disappears in
one step rather than file by file, so the Changes panel never fills with
deleted files while it goes. If deleting the remote branch fails, the local
removal still happens and the failure is reported.

### Clean up after deleting outside Tori

If a worktree folder was deleted in Finder or a terminal, git still has a
record of it. **Prune worktrees** on the project clears those records and says
how many it pruned.

### Remove worktrees automatically

Tori can remove worktrees for you. Both settings are off until you turn them on,
under **Cleanup** in Settings > Integrations:

- **Remove worktrees after merge**: removes a worktree once its pull request has
  merged and the worktree has nothing newer than the commit that merged. A
  squash merge counts, and so does a branch whose remote was deleted after the
  merge. This only covers projects in the active Space, because those are the
  ones Tori asks the host about.
- **Remove idle worktrees after**: Off, 3, 7, 14 or 30 days. Removes a worktree
  once that long has passed since it was created, since its last commit, and
  since a session in it last did anything, whichever is latest. Its branch must
  have no unpushed commits. This covers every Space.

Tori never removes:

- the main checkout, a [Topic's](/docs/workspace/topics/) worktree or a fan-out
  attempt
- a worktree on a detached HEAD, which has no branch to bring it back with
- a worktree with uncommitted changes
- a worktree an agent is running in, or one with a terminal or editor tab open
- a worktree whose [run command](#a-run-command-for-each-worktree) is running
- the worktree you have selected
- a worktree an autopilot item is still working in

It checks when Tori starts, when you change either setting, every hour, and
for a project's merged branches whenever pull request status refreshes. Just
before removing a worktree it checks for uncommitted changes once more.

The branch is always kept, so **Add Worktree** brings any of them back. Files
your `.gitignore` covers, like `node_modules` or `.env.local`, are removed with
the folder, the same as removing it by hand. Files in
[Shared files](/docs/git/shared-files/) are only links, so they are safe.
When a check removes anything, a message lists the branches.

## When the upstream was force-pushed

If someone force-pushed the remote branch over commits you have, pushing would
overwrite their update and pulling would merge two histories. Tori notices:
the branch's sync mark says the upstream was force-pushed over your commits,
and the branch menu offers **Reset to upstream**, which resets your branch to
the remote's. Commit or stash anything you want to keep first.

## The commit graph

**Graph** on a branch's menu opens its commit graph in a tab: every commit
as a lane, newest first. Click a commit to see the files it changed, and a file
to open that commit's diff. The same graph is in the Changes panel's history
section. See [The Changes panel](/docs/git/changes-panel/#graph-stashes-and-checkpoints).
